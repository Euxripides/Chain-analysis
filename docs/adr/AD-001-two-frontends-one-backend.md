# AD-001：两套前端、一个模块化单体后端

- 状态：Accepted
- 日期：2026-09-12
- 关联：`docs/dual-system-development-plan.md` §1、§3、§6.1、§6.2、§16

## 背景

当前是单个 SPA，把「用户业务」与「平台控制」混在同一套导航与同一份构建产物里。
计划要求升级为「用户层系统 + 后台管理系统」，共用可信数据、任务、证据与审计底座。

## 决策

1. 后端继续是 Go modular monolith，**不拆分微服务**。理由：当前规模下跨服务的一致性、事务与审计成本远高于收益。
2. 前端拆成两个独立可部署应用：`frontend/apps/user-console`（`/app-v2`）与 `frontend/apps/admin-console`（`/admin`）。
3. 两套前端共用 `frontend/packages/{design-tokens,ui,api-client}`，**不共享页面**。
4. 数据库与对象存储是唯一事实来源；两套系统不各自保存任务、用户或审计状态。
5. 短期共用 Go 二进制与 `internal/api` 包，但路由分区（`/api/v1`、`/api/v2`、`/api/admin/v1`、`/api/auth/v1`）并各自受独立中间件约束。

## 被否决的方案

- **微服务拆分**：14 周内无法同时完成拆分与安全闭环，且会破坏审计事务性。
- **单 SPA + 按角色隐藏菜单**：不满足"所有跨系统跳转必须重新检查服务端权限"，也无法独立发布与独立审计。
- **两套后端**：会产生用户、任务、审计的双写与不一致。

## 影响

- 构建产物从 1 个变成 3 个（旧 SPA + 2 个新应用），CI 与部署需要同时覆盖。
- 共享包必须保持"无反向依赖"：packages 不得 import apps。
- Nginx 需要新增两条上游路由。

## 回滚

删除 Nginx 中 `/admin/` 与 `/app-v2/` 两条 location 并停用两个 systemd 单元即可回到单 SPA；
后端路由分区是纯新增，不影响 `/api/v1` 兼容层。
